Inside the VSS Reader

VSS turns a typed request such as “add a red circle called Start” into an exact command the diagram engine can run. It is built from vector arithmetic instead of a transformer, it is small enough to run in a browser tab, and it is designed to hold back and ask when it is unsure.

What VSS is

VSS is one of the readers in the SOP Sketchpad, a diagram editor you talk to in English. A reader takes a typed message and writes it down as small, exact commands called wires. The engine runs the wires. No reader ever draws anything itself.

The name stands for VSA Semantic Space. VSA means vector symbolic architecture: every word becomes a long list of numbers, and simple arithmetic on those lists records which word fills which slot. There is no transformer inside.

Its goal comes from the project’s research question: build a reader that does only what it is sure of, says clearly where it is unsure, and asks about the rest. In the project’s scoring, one confident mistake costs as much as ten right answers.

One message, step by step

The shipped VSS (all nine worlds, the cutter and the context filler) was run in Node on the message below. The figure shows what it produced.

  1. Cut. A small tagger (an averaged perceptron) marks where each request starts and which worlds are likely to understand it. VSS reads one request at a time.
  2. Route. The three most likely worlds each read the request. The reading with the fewest words the world did not understand wins.
  3. Read. The winning world fills in a wire: the action and the value of each slot. A context step fills in references such as “it” or “the new diamond”.
  4. Gate. VSS scores its confidence in the reading. Above the threshold the engine runs the wire. Below it, VSS asks the person and says why.

The wires VSS wrote for the second message, “make Cart large and turn it green, then is Cart connected to Pay?”:

@s1 command  action=set target=Cart size=large
@s2 command  action=set target=Cart color=green
@s3 question ask=connected target=Cart anchor=Pay

How a word becomes numbers

  1. Fingerprint. Each word gets 1,024 angles generated from a SHA-256 hash of its text. The same word always gets the same fingerprint on any machine, and a word VSS has never seen simply gets a new one. Fingerprints are never trained.
  2. Address. Each word also gets an address, computed from its kind (colour, shape, verb, name and so on) and its neighbours. The table that turns kinds and neighbours into addresses is the route book, and it is the main thing VSS learns.
  3. One sum. VSS multiplies each word’s fingerprint by its address and adds everything into one vector, called S. To read a slot such as the colour, it multiplies S by the inverse of that slot’s key and checks which known word’s fingerprint matches best. The gap between the best and second-best match is its margin.

Multiplying two of these vectors adds their angles, so it can be undone exactly. Adding vectors piles them up, so every extra piece makes the others a little harder to read back. Try it below.

This is why VSS cuts a message into single requests before reading it. Its whole state is one vector of 1,024 numbers, and long inputs blur.

It is also why new names cause no trouble. A name’s fingerprint is generated, never learned, so nothing in the model depends on which names appeared in training. In the research repository’s synthetic test, the reader placed brand-new names correctly every time (1.000). A small transformer given the same input scored 0.215, close to the 0.167 chance level.

Nine small worlds

VSS is nine small models instead of one big one. The 51 actions are grouped by the slots they share and by which actions the reader tended to confuse. Help, for example, is a world of its own because its questions (“how do I…”) can mention any topic. The cutter decides which worlds read each request.

How it was trained

Everything VSS knows about English comes from example messages with the correct wires written next to them. The project’s rules forbid word lists, synonym tables and sentence templates inside the reader, so every mapping from words to actions has to be learned from those examples.

The training goal

For each labelled request, training builds two vectors: S from the words, using the current route book, and an answer vector from the labels, with each correct word bound to its slot’s key. The optimizer (Adam, learning rate 0.02, batch 8, 10 passes over the data, 1,024 dimensions, on a CUDA GPU) adjusts the route book so the two vectors point the same way, measured by their cosine. There are no negative examples. Fingerprints and slot keys never change, and word kinds are settled before this step, so only the route book moves.

The writers worked from the legend and the labelling rules; each wire records the exact words it came from and its trigger word. The test set used today (fresh2 and short3, 745 messages in its test part) was written later by Opus and is not in any training folder list.

How careful it is

VSS executes a request only when its confidence clears a threshold. The confidence is a logistic regression over 14 signals the pipeline records along the way, such as how cleanly the cut fell, how far ahead the winning world was, and the weakest slot margin. Raising the threshold buys fewer mistakes with less work done.

At the default setting, VSS carried out 94 actions on the test part and one of them was wrong (1.1%). The price is that it did only 5.3% of the requested actions itself and asked about 72.6% of requests.

Where it falls short

  • It does little on its own. At the default setting it executes about one request in twenty and asks about most of the rest. That is the intended trade, but it is a large one.
  • Its own margin says little. Used alone as a confidence, the margin separated right from wrong readings with an AUROC of about 0.58, barely above a coin flip (0.5). The 14-signal confidence reaches 0.779 out-of-fold on its calibration set. The 0.05 abstain cut-off on the margin was stated, not fitted.
  • One request at a time. Long input blurs the single state vector, so everything depends on the cutter. A bad cut carries through to the reading.
  • New writers hurt. On text from a writer it had never seen, the earlier VSS went from 3.4% to 7.3% wrong among executed actions.
  • The spec is out of date on test sets. VSS_READER_SPEC.md still says the llm_bench/sonnet and llm_bench/haiku test sets are never used for anything else. Since the owner’s decision of 2026-11-01 (AGENTS.md) there is no hidden test set, and labelled versions of those messages are now training data (front.py, lines 707 to 710). The test figures on this page come from the test part of fresh2 and short3, which is in no training folder list.
  • Training logs are missing. The run logs named in the nine worlds’ BUILD.json files are not in training/sketch/runs/, which holds logs of the previous seven-world version, so the training time of the shipped worlds is not recorded.
  • The research numbers are synthetic. The 1.000 against 0.215 result on new names comes from template-generated test worlds. It shows a property of the design, not the quality of the diagram reader.
